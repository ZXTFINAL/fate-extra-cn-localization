# 方法论：可迁移的汉化工程做法

这份文档不是 Fate/Extra 专用，而是从这次工程里抽出来的通用方法。换一个游戏、换一种资源格式，下面的原则仍然成立。

---

## 1. 证据等级

任何关于格式的结论，按可信度排序：

| 等级 | 证据 | 例子 |
|---|---|---|
| E1 | 运行时观测 | 实机/模拟器截图、内存断点 |
| E2 | 可执行文件反汇编 | `CPoem` 以 14 调用格尺寸设置函数 |
| E3 | 真实资源字节 + 可复现采样 | 用 14px 网格采样得到与截图相关的碎片 |
| E4 | 同引擎其他游戏的公开实现 | ccc-tl 的 CPK/PAK 读取器 |
| E5 | 文档/论坛/推测 | "应该也是 16px" |

规则：

- **E4/E5 只能用来提出假设，不能作为结论**。本项目最初的诗文错误，正是把正文字库的 E3 结论（16px）错误推广到诗文（另一套资源）。
- 每个 E2 结论要给出地址、指令、参数；每个 E3 结论要给出输入哈希与复现脚本。
- 报告里标明证据等级。没有 E1 就不写"实机验证通过"。

---

## 2. 先复现，再修复

修一个缺陷前，先做三件事：

1. **保留现场**：原资源、原产物、截图、哈希。
2. **独立复现**：写一个只依赖小快照的脚本，不依赖旧构建目录。
3. **量化吻合**：把复现结果与现象做数值比较（相关性、像素差、哈希），而不是"看起来像"。

诗文案例：

- 复现脚本只读 `0000.dat`、`poem.bin`、`poem_font.txb` 三个小文件；
- 采样出的碎片与截图相关性 0.96；
- 修复后用同一脚本采样，得到完整文本。

好处：修复不是"改到不碎为止"，而是"根因被证明消除"。

---

## 3. 一次只改一类

把变更分成互不重叠的类别，每类一个脚本、一份报告：

| 类别 | 脚本 | 不碰什么 |
|---|---|---|
| 提取 | `dump_*` | 不改源 |
| 语义翻译 | 批次/合并 | 不改控制码结构 |
| 排版 | `fix_*_layout` | 不改语义 |
| 字库 | `patch_*_font` | 不改文本 |
| 图片 | `patch_*_image_text` | 不改文本/字库 |
| 打包 | `build_*` | 不做内容判断 |
| 写回 | `embed_*` | 不做资源转换 |

为什么：

- 出问题时能定位到"哪一类"；
- 每类可以单独回滚；
- 报告的数字有意义（"1,186 条文本变更"而不是"改了一堆东西"）。

反例：把翻译、换行、补字混在一个脚本里，字库字数变了却不知道是译文变长还是排版加了字。

## 4. 幂等与回环

任何"解码 → 编码"必须满足：

```
encode(decode(x)) == x   # 对未修改的输入
```

这是编辑器的安全底线。不满足就不能保证"只改了我想改的像素"。

实现要点：

- 保留原始块引用、调色板、对齐填充、空条目；
- 不以"重新生成"代替"原地保留"；
- 每次编辑前先跑一次回环，失败即拒绝。

本项目用它守住了：

- 200 个 UI TXB / 1,627 个 TEX 的未修改部分；
- 未变更的 PAK 成员；
- 字库的非目标页。

## 5. 稳定标识

翻译表的主键不能是"行号"或"文件偏移"，因为：

- 重打包会改偏移；
- 同一句在多处复用；
- 批次合并会改变顺序。

用**源内容哈希**做 ID：

```
id = sha256(原始字节)[:16]
```

收益：

- 与位置解耦；
- 复用自动合并；
- 批次可以乱序合并；
- 审计可以按 ID 追踪到所有引用。

代价：

- 改原文会改 ID。因此原文视为不可变；要修原文，建立显式映射，不静默重算。

## 6. 分层验证

| 层 | 问题 | 手段 | 结论措辞 |
|---|---|---|---|
| L1 结构 | 数据是否合法 | 回环、哈希、指针、组数 | "结构校验通过" |
| L2 语义 | 意思是否对 | 逐句阅读、上下文、术语 | "已读 N 条，修正 M 条" |
| L3 运行时 | 游戏是否正常 | 模拟器/实机 | "在 X 路径上运行通过" |

禁止跨层表述：

- L1 通过 ≠ 译文正确；
- L2 读过一部分 ≠ 全量正确；
- L3 抽检通过 ≠ 所有分支正常。

发布说明必须分别写三层，并给出未覆盖范围。

## 7. 语境校对的分片方法

### 7.1 按源顺序，不按 ID

```python
refs.sort(key=lambda r: (r["file"], r["text_offset"]))
```

同一场景的对话在源文件中连续，按偏移排序才能还原"上一句—下一句"。

### 7.2 连续窗口 + 前后文

每包取同一脚本 ≤ 80 行源范围，附前后各 ≤ 8 行。目标句在窗口中，审阅者能看到说话人、动作、回应。

### 7.3 一个 ID 只分配一个主位置

同一句在 10 个文件复用，只在一个"最有上下文"的位置精读；其他位置在发现歧义时追查。否则工作量爆炸且重复。

### 7.4 分 lane 并行

把分片分成若干 lane，每 lane 独立进度文件：

```json
{"target_count": 6356, "reviewed_target_ids": [...], "reviewed_shards": [...]}
```

进度只记真实读过的 ID。空文件就是 0，不预填、不批量勾选。

### 7.5 三类结果

- 已读无需改；
- 建议修正（写 `id / zh_cn / reason`）；
- 未决（记下疑点，不强行改）。

## 8. 语义审计的高频错误模式

跨游戏通用：

| 模式 | 日文信号 | 中文陷阱 |
|---|---|---|
| 省略主语 | 无代词 | 补错人称 |
| 授受关系 | `てくれる/てもらう/てあげる` | "他给我" vs "我给他" |
| 限制/否定 | `しか…ない`、`わけではない` | 译成肯定或反义 |
| 反问 | `じゃないか`、`のではないか` | 译成否定陈述 |
| 多义词 | `付き合う`、`受ける`、`挨拶` | 按词典首义硬译 |
| 引述 | `と言っていた`、`部長の話` | 把"说的话"译成"人的事" |
| 双重否定 | `ないわけにはいかない` | 漏一层 |
| 敬语/亲疏 | `ご主人様`、`奏者` | 统一成一个词，丢关系 |
| 伏笔 | 重复、异常日常、姓名双关 | 当普通叙述抹平 |

做法：先标记信号，再读上下文，最后改；不要用正则批量替换语义。

## 9. 工具设计原则

### 9.1 配置驱动

内容替换（图片矩形、文本块）放在 JSON 里，脚本只执行。好处：

- 可 review；
- 可 diff；
- 可重放；
- 不把文案硬编码进代码。

### 9.2 默认不破坏

- 输出到独立目录，不覆盖源；
- 修改前备份（`text.pre-*.jsonl`）；
- 提供 `--prepare-only` / dry-run；
- 未声明的文件不输出。

### 9.3 失败要早

- 输入哈希不符 → 中止；
- 旧字节不符 → 中止；
- 文本超出矩形 → 中止；
- 映射缺失 → 中止。

宁可构建失败，也不要产出"看起来成功但有一屏错字"的包。

### 9.4 报告即证据

每次构建输出：

- 输入/输出哈希；
- 变更计数；
- 逐文件/逐资源清单；
- 校验结果。

没有报告的构建视为未完成。

## 10. 文档写法

### 10.1 区分"事实 / 推断 / 未验证"

```markdown
事实：EBOOT VA 0xA6254 传入 0xE。
推断：因此格尺寸为 14。
未验证：运行时页数上限。
```

### 10.2 数字要能复算

写"1,133 条修正"时，同时给：

- 源表哈希；
- 修正表哈希；
- 统计脚本或字段。

### 10.3 不用"全部/完美/彻底"

除非有对应的全量证据。更准确的写法：

- "开场三场景 641 ID 已逐段阅读"；
- "`/interface/` 下 466 个目标已完成"；
- "lane 1 已读 1,452 / 6,356"。

## 11. 新项目启动清单

1. **确认版本**：镜像号、区域、可执行文件哈希。
2. **只读源**：挂载/复制，永不原地改。
3. **盘点容器**：条目数、类型、对齐、压缩。
4. **找到文本真源**：不是"所有可打印字节"，而是指令引用的字符串。
5. **建立稳定 ID**：内容哈希，位置无关。
6. **做最小闭环**：100 条文本 → 重建 → 写回 → 启动。
7. **再碰字库**：确认格尺寸、每页字数、运行时上限，三者缺一不可。
8. **再碰图片**：先证明解码/编码幂等，再改像素。
9. **最后做语义**：按源顺序读上下文，分片、分 lane、记进度。
10. **每步留证据**：哈希、报告、复现脚本、未完成清单。

## 12. 一句话

> **格式靠证据，变更靠隔离，质量靠分层，进度靠诚实。**
