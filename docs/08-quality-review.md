# 质量流程：如何避免"译完了"的假象

翻译覆盖率 99.99% 不代表质量合格。真正的问题集中在三类：

1. **结构性错误**：控制码缺失、指针错位、字库缺字、图片没替换；
2. **语义性错误**：人称反了、否定反了、多义词选错、引述关系错；
3. **语境性错误**：单句看没问题，放进前后文就说不通。

本工程把质量拆成可独立执行的审计，每类都有明确的证据标准与"未完成"边界。

---

## 1. 三层验证

| 层 | 目标 | 手段 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|
| L1 结构 | 字节/格式正确 | 回环编码、哈希、指针校验、组数统计 | 数据没坏 | 译文是否通顺 |
| L2 语义 | 句意/人称/术语正确 | 逐句阅读、上下文窗口、术语表 | 读过的句子正确 | 未读的句子正确 |
| L3 运行时 | 游戏里真的对 | PPSSPP/实机走查 | 特定路径可运行 | 全部分支都覆盖 |

报告必须标明结论属于哪一层。把 L1 通过写成"汉化完成"是常见误导。

---

## 2. 语境校对

### 2.1 为什么不能按 ID 顺序读

`text.jsonl` 的 ID 是哈希，按 ID 排序会把同一场景的对话打散。正确做法是**按源文件 + 文本偏移排序**，还原真实对话顺序：

```python
refs.sort(key=lambda r: (r["file"], r["text_offset"]))
```

这样能看到"上一句谁说的、下一句谁回应"，才能判断：

- 省略的主语是谁；
- `付き合う` 是"配合检查"还是"交往"；
- `しか` 是"只"还是"连……都不"；
- `じゃない` 是否定、反问还是口语确认；
- 引述的 `目の前` 是说话人眼前还是玩家眼前。

### 2.2 开场三场景

第一轮精读覆盖：

| 场景 | 源文件 | 引用数 | 唯一 ID | 建议修改 |
|---|---|---:|---:|---:|
| 走廊 | `000003/field/003/0000.dat` | 306 | 298 | 22 |
| 教室 | `000009/field/009/0000.dat` | 241 | 238 | 23 |
| 校门 | `000016/field/016/0000.dat` | 118 | 105 | 14 |
| 合计 | | 665 | 641 | 59 |

这 641 个 ID 是**已逐段阅读**的，不是全量 19,711 的完成证明。

### 2.3 发现的错误类型

| 类型 | 例子 | 教训 |
|---|---|---|
| 人称/施受 | 一成被写成"她"；老师的失忆被写成玩家的失忆；Archer 安慰玩家的"你"被写成"他" | 必须确认说话人与动作承担者 |
| 否定/限制 | `名前しか知らない` 译成"连名字都不知道"（反义）；`２－Ａじゃない` 译成"这里又不是 2-A" | `しか`、`じゃない` 是高频陷阱 |
| 多义词 | `付き合う`（配合检查/交往）、`御挨拶`（反讽）、`テストを受ける`（参加考试） | 依赖前后句，不能查词典定死 |
| 引述/接续 | `部長の話` 是"部长说的话"，不是"部长先生的事"；`待ちかねた` 是说话人在等玩家 | 谁等谁、谁说谁，要按场景 |
| 叙事伏笔 | "初次经历却早已知道"是循环伏笔；`勝ち残った` 不等于"活到最后" | 不能把伏笔解释成普通叙述 |

### 2.4 全量分片计划

剩余的 19,711 个 ID 生成 609 个审阅包：

- 每个 ID 只分配一次"主要审阅位置"；
- 每包取同一源脚本的连续窗口（≤ 80 行源范围），附前后各 ≤ 8 行上下文；
- 对话优先于选项/说明/名称；
- 每个包带 `is_review_target`、`reviewed_by_opening_pass`、场景、偏移、原文、当前译文。

分三条 lane，各约 6,356 个目标：

| lane | 目标数 | 已读 | 修正 |
|---|---:|---:|---:|
| lane 1 | 6,356 | 1,452 | 138 |
| lane 2 | 6,357 | 0 | 0 |
| lane 3 | 6,357 | 0 | 0 |
| 合计 | 19,070 | 1,452 | 138 |

三条 lane 覆盖的是**开场 641 ID 之外**的 19,070 个目标；加上开场，正好 19,711。

**未读就是未读**。lane 2/3 的进度文件为空，报告不会把它们写成"已校对"。

### 2.5 检索线索不是结论

对全量文本做的风险检索：

| 线索 | 命中 ID | 用途 |
|---|---:|---|
| 中文补了人称、日文无明显代词 | 7,722 | 核对省略主语 |
| ruby 双层 | 1,830 | 区分读音与双关 |
| `しか` 限制结构 | 787 | 查"只/连……都不"反向 |
| 异常/记忆/姓名/重复叙述 | 690 | 保留循环世界伏笔 |
| `じゃない` | 409 | 否定/反问/确认 |
| 男女分支控制 | 288 | 保留分支，不合并 |
| `付き合う` | 29 | 按语境区分 |

这些是**候选风险**，不是"已确认错误"。把它们当错误批量改，会制造新错误。

## 3. ruby 专项审计

独立于普通文本，因为双层结构有额外的结构约束：

1. 统计所有 `#RUBS... #RUBE... #REND`；
2. 检查每条译文的组数是否与原文一致；
3. 检查是否存在上下层完全同文（说明把读音层重复译了）；
4. 检查缺失 `#REND`、颜色码范围错位；
5. 逐类决定保留/取消（详见 [05-poem-and-ruby.md](05-poem-and-ruby.md)）。

结果：1,133 条修正，结构缺损 0，组数不符 0，同文组 0。

审计文件：

- `data/review/ruby-fixes.jsonl`：最终修正（1,133 条）；
- `data/review/ruby-final-audit.json`：统计与缺字表；
- `data/review/ruby-audit.md`：结论与证据；
- `data/review/ruby-font-audit.md`：字库格式与扩容方案。

## 4. UI 图片审计

图片不能靠"看起来对"，必须做像素级验证：

1. 未修改 TEX 解码→编码逐字节相同；
2. 输出 TXB 再解析，条目名/顺序/尺寸/调色板逐项相同；
3. 每个编辑目标的索引图与预期像素一致；
4. 文本超出声明矩形时渲染器拒绝；
5. 视觉抽检启动声明、教程、混合字图、边框。

结果：200 个原 TXB、1,627 个非空 TEX 全部回环通过；371 个输出 TXB 0 错误。

## 5. 审阅者的工作规范

### 5.1 包内流程

对每个审阅包：

1. 读完整窗口（含前后文），不要只看目标句；
2. 标记三类结果：`已读无需改` / `建议修正` / `未决`；
3. 修正写入独立 JSONL（`id / zh_cn / reason`），**不直接改主表**；
4. 同一 ID 的重复引用只产生一条修正；
5. 遇到人称/否定错误，顺藤摸瓜查所有复用引用，不只改当前一处。

### 5.2 修正理由要可复核

`reason` 不是"润色"，要写清依据：

- "原文 `彼女`，前句指新闻部长，故改她"；
- "`しか` + 否定，原译反义"；
- "同一 ID 在 000003 与 000016 均出现，统一改"。

### 5.3 禁止事项

- 不凭 ID 相邻猜上下文；
- 不把检索命中当错误；
- 不为"通顺"删掉分支/控制码；
- 不把普通日文读音硬贴到中文正文；
- 不在未读的情况下勾选"已审"。

## 7. 发布前的门槛

一个版本可以发布，至少满足：

- [ ] 所有译文可编码，构建 0 异常；
- [ ] 关键资源回环通过；
- [ ] v14→新版的所有变更都有报告与哈希；
- [ ] PPSSPP 从新游戏到至少第一场战斗无崩溃；
- [ ] 已知问题清单更新；
- [ ] 发布说明写明"未完成项"，不用"完美汉化"。

实机/全分支回归未完成时，版本号标 `-pre` 或明确写"资源预备版"。
