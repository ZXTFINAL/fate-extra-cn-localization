# 文件格式笔记

本文件记录**经实际字节验证**的格式结论。未验证的推测会明确标注。所有偏移均为文件内字节偏移，多字节整数除特别说明外为小端。

---

## 1. CPK（`data.cpk`）

CRI CPK 容器，头部是一个 UTF 表（`@UTF`），不是固定结构体。

| 位置 | 内容 |
|---|---|
| `0x00` | 头部前缀，`0x10` 处为 `CpkHeader` UTF 帧 |
| `TocOffset` | 条目表 UTF 帧偏移 |
| `ContentBase` | 内容区基准（本作为 `0x800`） |
| `EtocOffset / EtocSize` | 扩展表，重建时原样搬运 |
| `ContentSize` | 内容区大小 |

条目表每行包含 `DirName`、`FileName`、`FileOffset`、`FileSize`、`ExtractSize` 等字段。`FileOffset` 是相对 `ContentBase` 的偏移。

本作实测：

- TOC 5,824 行；
- 解包器处理 2,297 个 DAT/PAK/CMP 条目；
- 成功解开 2,240 个包；
- 内容按 2,048 字节对齐。

重建时不能只改文件内容：长度变化会移动后续所有条目，必须同步重写 TOC 的 `FileOffset/FileSize/ExtractSize`、头部 `EtocOffset/ContentSize`，并把 ETOC 搬到新位置。

## 2. PAK / TXB（包容器）

PAK 与 TXB 是同一套容器，区别在成员类型：PAK 装数据文件，TXB 装 TEX 纹理。

```
uint16 count
uint16 flags        # 0x8000 = 带 64 字节路径名
uint32 size[count]
padding to 16
payload[0..count-1] # 若带路径，每个 payload 前有 64 字节名字
```

要点：

- 长度表在头部，条目内容连续存放，**不保证**每个条目单独对齐。
- 带路径时，名字是 64 字节定长，Shift-JIS，NUL 填充；名字位于对应 payload 之前，不在头部。
- 重写时若只设置 `flags=0x8000` 却不写 64 字节名字，游戏会读到位移错乱的数据。`write_font_txb` 的历史实现就有这个限制，ruby 字库不能直接调用。
- TXB 的成员名形如 `font08_00.tex`、`mode_help_00.tex`，是 TEX 条目名而非外部路径。

## 3. CMP（IECP 压缩）

```
"IECP"
uint32 uncompressed_size
LZSS 流
```

LZSS 参数（由编码器实现与实测反推）：

| 参数 | 值 |
|---|---|
| 窗口 | 4,096 字节 |
| 最短匹配 | 3 |
| 最长匹配 | 18 |
| 距离编码 | `(0xFEE + match_pos) & 0xFFF` |
| 标志位 | 每个控制字节 8 位，1 = 字面量，0 = 匹配 |

`build_fate_extra.encode_cmp` 是可用的参考实现：4 KiB 窗口、3–18 匹配、每 8 个 token 一个控制字节。压缩率不是最优，但产物能被游戏正确解压。

解包时不要假设压缩流长度等于文件长度；以 `uncompressed_size` 为准，并允许尾部对齐填充。

## 4. DAT（场景字节码）

DAT 是 32 位小端字节码，字符串以 Shift-JIS 存储、NUL 结尾，由指令中的绝对偏移引用。

已确认的文本相关操作码：

| 操作码 | 含义 | 处理 |
|---|---|---|
| `0x3926` | 对话文本 | 可换行、可改长度 |
| `0x1530` | 回想/日志文本 | 同上 |
| `0x0126` | 动画章节卡文本（motion） | 不插换行，走诗文专用字库 |
| `0x0200` | wait | 调整章节卡停留时间时使用 |
| `0x1401` | call | 章节卡调用 |

转储器不按"所有可打印字节"猜文本，而是沿这些操作码找指针，再解析目标偏移处的 NUL 结尾字符串。这样能避免把二进制误当文本，也能拿到准确的 `pointer_offsets`。

替换规则：

- 新串 ≤ 原串：原地写，**剩余槽位全部清零**。部分渲染器按存储字符数读取，只写 NUL 不擦尾会残留旧字。
- 新串 > 原串：追加到 DAT 末尾（含 NUL），把所有指向旧串的指针改为新偏移。
- 文件末尾按 16 字节对齐。

## 5. TEX（PSP 纹理）

TEX 头 48（`0x30`）字节：

| 偏移 | 字段 | 说明 |
|---|---|---|
| `+0x10` | texture type | 4 = T4（4bpp），8 = T8（8bpp） |
| `+0x12` | swizzled | 1 = PSP 块交错 |
| `+0x14` | width | 逻辑宽 |
| `+0x16` | height | 逻辑高 |
| `+0x1C` | data_size | 像素数据字节数 |
| `+0x30` | 像素数据 | 长度 = `data_size` |
| 数据后 | CLUT | 调色板头 + 索引/颜色 |

PSP swizzle：

- 以 **16 字节 × 8 行**为一块交错；
- T4 每字节低 nibble 是左像素、高 nibble 是右像素；
- T8 每字节一个像素；
- 解包高度应由 `data_size` 推导，不能只用逻辑高度。ruby 第二页逻辑高 130、存储高 136 就是典型例子。

CLUT / CCT：

- 20 字节头，后接 `int16` 索引；
- `-1` 表示空块，且不计入非空计数；
- 调色板长度按色数与模式计算，**不要信任 `palByteSize` 字段**；
- 重编码时必须保留原调色板、唯一块与未变块的引用关系，否则会改变无关像素。

`fate_extra_texture.py` 的硬性保证：未修改的索引图解码后再编码，逐字节相同。这是做 UI 图片替换的前提。

## 6. 正文字库（`kanzi.bin` + `font.txb`）

### 6.1 `kanzi.bin`

```
uint32 count
record[count]   # 每条 6 字节
```

每条记录：

| 字节 | 内容 |
|---|---|
| 0–1 | CP932 码位，**小端存储**（游戏内字节 `81 45` 在此写作 `45 81`） |
| 2–4 | 该字的 UTF-8（BMP，最多 3 字节） |
| 5 | `0x00` |

记录顺序 = 字库图集索引。原文 3,040 条。

### 6.2 `font.txb`

- 每页 256×256，T4，swizzled；
- 字格 16×16，16 列 × 16 行 = **256 字/页**；
- 页数随字数增长，v14 为 16 页；
- 运行时索引上限 **4,096**（16 页 × 256）。

### 6.3 补字策略

1. 能用原生 CP932 表示且原字库已存在的字，直接复用。
2. 原生 CP932 无此字（简体专有字、部分标点），分配 CP932 用户区 `0xE000` 起的别名；`kanzi.bin` 追加记录，`glyph-map.json` 记录 `汉字 → 别名`。
3. 原生 CP932 有、但原字库没有的字，同样走别名，避免占用日文字位。
4. **绝不重排已有别名**。旧译文已按旧别名编码，重排会造成大面积错字。
5. 字数超过 4,096 时，只能删除"已无任何引用"的日文字形；不能删除仍可能出现在未提取 UI 中的字。

## 7. 诗文（poem）字库

资源：

- `interface/poem/poem.bin`：记录数 + 每条 6 字节（前 2 字节为 `(lead<<8)|trail` 的 CP932 键，后接 UTF-8 显示串）；
- `interface/poem/poem_font.txb`：256×256 T4，**14×14 格，18 列 × 18 行 = 324 字/页**。

运行时公式（由 EBOOT 反汇编确认，VA `0xB553C`–`0xB6534`）：

```
columns = 256 // 14 = 18
perPage = 18 * 18 = 324
page    = index // 324
within  = index % 324
u       = (within % 18) * 14
v       = (within // 18) * 14
采样矩形 = (u, v, u + 13, v + 13)
```

`CPoem` 在 VA `0xA6254` 调用 `0xACD0C`，参数 `a1=a2=0xE`（14），这是格尺寸的直接证据。ruby 字库另设 9×9，不能混用。

原版 `poem.bin` 记录数 405，`poem_font.txb` 2 页。修复后的中文字库包含 396 个字形，0 空字、0 映射错位，且最后一列/行保持透明以避免采样到邻格。

## 8. ruby（双层表记）字库

### 8.1 文本控件码

语法：`#RUBS小字层#RUBE正文层#REND`

- `RUBS` 是上标/小字，`RUBE` 是正文；
- `#REND` 结束；
- 小字层使用独立字库，正文层使用正文字库；
- 颜色码 `#C123456789` / `#CDEF` 可嵌套，计量宽度时必须剔除。

上下层顺序的证据：日文 `#RUBSしんじ#RUBE慎二#REND`（读音/汉字）、`#RUBSマスター#RUBE奏者#REND`（外来语/意译）；原 `ruby.bin` 219 字全部是假名、全角 Latin 与少量符号，汉字为 0，正好只能承载第一段。

### 8.2 `ruby.bin`

```
uint32 count
record[count]   # 6 字节，格式同 kanzi.bin
padding to 16
```

原 219 条，结束于 `0x526`，后 10 字节为零。

### 8.3 `ruby.txb`

- 带 64 字节路径名的 PAK（`count=2`, `flags=0x8000`）；
- 两张 TEX：`font08_00.tex` 128×128、`font08_01.tex` 128×130（存储 128×136）；
- T4，128 像素宽；
- **9×9 像素槽，14 列 × 14 行 = 196 字/页**；
- 坐标：`page = index // 196`、`tile = index % 196`、`x = (tile % 14) * 9`、`y = (tile // 14) * 9`；
- 原字并非都在 8×8 内：`ｇｊｐｑｙ` 用第 9 行，`ばふむももりオネ` 用第 9 列，不能裁成 8×8；
- 两页 392 槽，原用 219，余 173。

### 8.4 扩容结论

按 ruby 审计后的最终需求：

- 上标共 349 种字符；
- 原表缺 299 种（297 汉字 + `．` + `－`），2,541 字次；
- 保留原 219 + 新增 299 = **518 条，3 页**；
- 新字沿用正文 `glyph-map.json` 的别名，不为 ruby 单独分配编码。

## 9. ISO9660

- 主卷描述符在扇区 16（`0x8000`），签名 `CD001`；
- 卷大小在 PVD `+80`（小端）与 `+84`（大端），两处必须一致；
- 目录记录含 extent LBA 与 data length（小端/大端各一份）；
- `data.cpk` 变大时，需要允许占用后续空闲扇区并更新卷大小；
- 游戏按**小写** `data.cpk` 查找。若重建工具把标识写成大写，需用 `patch_fate_extra_iso_case.py` 恢复。

## 10. 未验证/待确认

以下内容没有足够证据，文档中不作为结论使用：

- 缺字时运行时的具体回退行为（空白、替代框或其他）；
- 不同 PSP 固件/PPSSPP 版本对超大 CPK 的兼容差异；
- 部分 UI 纹理是否被其他场景以别名方式引用（已按 SHA-256 分组复制，但仍需实机走查）。
