## 2. 汉化涉及的五种"文本"

Fate/Extra 的日文并不只在一张文本表里。工程把它们拆成五类，分别处理：

| 类型 | 载体 | 数量级 | 处理方式 |
|---|---|---|---|
| 剧情/对话文本 | DAT 字节码中的 Shift-JIS 字符串 | 19,711 条唯一文本，408,418 处引用 | 提取 → 翻译 → 追加字符串 → 重写指针 |
| 正文位图字 | `PRELOAD/kanzi.bin` + `font.txb` | 原 3,040 字 → 压缩后 4,096 字 | 分配 CP932 用户区别名，渲染 16×16 字格 |
| 诗文/章节卡 | `interface/poem/poem.bin` + `poem_font.txb` | 405 条记录，396 个中文字形 | 独立 14×14 格、324 字/页字库 |
| 注音小字（ruby） | `PRELOAD/ruby.bin` + `ruby.txb` | 原 219 字 → 518 字 / 3 页 | 独立 9×9 槽、196 字/页字库 |
| UI 图片字 | `interface/**/*.txb` 内的 TEX 纹理 | 371 个 TXB，2,598 个 TEX 变更 | 解码索引图 → 擦字 → 绘制中文 → 重新量化/编码 |

任何一类漏掉，都会出现"正文是中文、界面还是日文"或"字显示成方块/碎字"的现象。这是本项目按类型拆分流水线的根本原因。

```
源 ISO（只读）
   │

   │                                  ├─ dump_fate_extra_text.py ──► text.jsonl + refs.jsonl
   │                                  │                                   │
   │                                  │                           翻译 / 批次合并 / 排版
   │                                  │                                   │
   │                                  └─ patch_fate_extra_font.py ──► 字库覆盖资源
   │                                                                      │

   │                                                   │
```

v15 走的是"增量修订"路线：不重新全量构建，而是在 v14 的 CPK 上按引用逐条替换，未变更成员直接取自可用的旧包，避免旧解包数据回退。

## 4. 为什么需要这么多脚本

单看每一类都简单，难点在交叉约束：

- 译文比原文长 → 不能原地覆盖，必须把新串追加到 DAT 末尾并改所有指针；
- 追加字符串会改变文件长度 → 外层 PAK 长度、CMP 压缩流、CPK 目录偏移都要级联更新；
- CPK 变大 → ISO9660 目录记录和卷大小都要改，否则游戏读不到；
- 新字需要字形 → 字库页数、字格网格、运行时索引上限（4,096）同时约束；
- 诗文和 ruby 各有独立网格 → 不能复用正文字库的 16×16 / 256 字每页假设；
- 控件码与换行会改变渲染宽度 → 排版必须在语义翻译之后、字体分配之前单独跑一遍。

因此脚本按"一次只做一类变更"切分，每步都有可检查的输入输出，而不是一个大而全的转换器。

## 5. 质量主张

本工程对"完成"的定义是：

1. **可复现**：从原盘和仓库脚本能重建同一产物；关键产物有 SHA-256。
2. **可追溯**：每条译文有稳定 ID，每个 ID 能回到文件、偏移与引用位置。
3. **可回滚**：每次批量修改前保留 `text.pre-*.jsonl` 快照。
4. **不夸大**：静态审计与实机验证分开陈述；未读过的文本不标记为"已校对"。

具体执行标准见 [08-quality-review.md](08-quality-review.md) 与 [methodology.md](methodology.md)。
